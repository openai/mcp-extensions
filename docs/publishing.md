# Releasing the Python and Node packages

Python (`openai-mcp-extensions`) and Node (`@openai/mcp-extensions`) have **independent versions and release PRs**. A Python change does not require a Node release, or vice versa. The Early-Access repository's `v0.1.0` GitHub release is historical and is not imported into the fresh destination; new tags are `python-v<version>` and `node-v<version>`.

## What is configured in code

- `release-please-config.json` selects the native Python and Node strategies for `python/` and `typescript/`, with separate PRs and changelogs. The manifest records each package's current version, initially `0.1.0`. There is no linked-versions plugin. The bootstrap SHA excludes history predating this setup; review the first proposed versions and notes.
- `.github/workflows/release.yml` runs release-please on `main` when enabled. Merging a generated release PR creates that package's tag and GitHub release, runs the shared checks against its exact release SHA, and optionally publishes its artifacts using OIDC.
- `.github/workflows/checks.yml` rehearses the pinned release-please library without GitHub writes, checking separate version bumps, generated-file formatting, and component release tags. It is reused by ordinary CI and releases: formatting, lint, types, builds, package metadata/export checks, wheel and sdist validation, and an isolated wheel installation. `python -m build` builds the wheel from the sdist. Before executing any tagged code, trusted inline workflow steps verify that the release tag identifies the checked-out commit and that this commit is on main. Package validation then checks each version against its own manifest entry and the selected release version.
- `.github/workflows/ci.yml` keeps the existing marketplace publication after successful main checks. Calling the shared checks for a package release does not republish the marketplace.
- Publishing jobs download only their current run's checked artifacts. They do not check out or rebuild source. Only upload jobs receive `id-token: write`; dependency downloads use Socket, while uploads target the production registries.
- Package repository metadata points at the intended `openai/mcp-extensions` identity. The Node library is publishable with public access; the workspace and plugin remain private. Removing `private: true` does not itself upload anything.

The old merged-PR `release` label workflow is replaced. Do not manually bump both versions or create a shared `v` tag. Stable numeric versions are supported; prerelease channels require an intentional workflow/config change.

## Activation checklist

**Merging this setup alone does not publish a package or enable release-please.** The following are repository variables, not secrets. Leave them unset or `false` until the corresponding setup is complete:

| Variable                 | Enables                                    |
| ------------------------ | ------------------------------------------ |
| `RELEASE_PLEASE_ENABLED` | Release PRs and GitHub releases            |
| `PUBLISH_PYPI_ENABLED`   | Public PyPI uploads after a Python release |
| `PUBLISH_NPM_ENABLED`    | Public npm uploads after a Node release    |

Registry upload jobs also require the exact repository identity `openai/mcp-extensions`. This is the production destination. Confirm launch approval before making the repository public or enabling package uploads. Copying code alone does not transfer repository settings or optional GitHub App access. For a fresh repository, import the reviewed source as its root commit with release-please disabled, then set `bootstrap-sha` to that new root commit in a follow-up change before activation. There is no pre-import destination commit in an empty repository. The workflow checks that the configured cutoff exists in main history before it allows release-please to run. This checkout uses that root commit as its cutoff; if the import commit changes, update the cutoff again.

1. **No SDK GitHub App is required.** Release-please defaults to the repository's built-in `GITHUB_TOKEN`, with Contents, Issues, and Pull requests write permissions scoped to its job. In **Settings → Actions → General → Workflow permissions**, enable **Allow GitHub Actions to create and approve pull requests**. Organization policy must permit this setting; the workflow does not approve or merge PRs. No PAT or new secret is needed. GitHub places CI for PRs created or updated with `GITHUB_TOKEN` in an approval-required state: review the generated changes, select **Approve workflows to run** in the release PR's merge box, and wait for the required `check` before merging. See [GitHub's workflow trigger behavior](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/trigger-a-workflow).

   **Optional App mode:** if the team already has access to the SDK release App, install/authorize it for this repository, set the repository variable `USE_SDK_RELEASE_APP=true`, and supply `OPENAI_SDKS_APP_CLIENT_ID` and secret `OPENAI_SDKS_APP_PRIVATE_KEY` in the `release` environment. The App needs Contents, Issues, and Pull requests write access. This mode lets release PR CI start automatically without the token-created PR approval prompt. Missing or invalid App credentials fail the job when App mode is explicitly selected. App credentials are separate from registry OIDC.

2. Create GitHub environments `release`, `pypi`, and `npm`, restricted to the `main` branch. Require publishing reviewers for `pypi` and `npm`, prevent self-review and administrator bypass where supported. Verify that the repository's GitHub plan supports the configured protections. Protect main and workflow changes with review and required CI. The final `check` gate preserves the status name already required by this repository's branch rules.
3. PyPI is already configured: project `openai-mcp-extensions`, organization `openai`, GitHub owner `openai`, repository `mcp-extensions`, workflow filename `release.yml`, environment `pypi`. Do not add a PyPI token or additional developers. [Publisher settings](https://pypi.org/manage/project/openai-mcp-extensions/settings/publishing/).
4. npm still needs its one-time bootstrap. npm requires the package to exist before configuring a Trusted Publisher. An existing npm maintainer should create it at the approved visibility; do not publish the prepared public tarball merely to reserve the name. A private, minimal placeholder at a different version (for example `0.0.0`) is an option if the organization has a paid plan. Its initial publish must use existing maintainer authentication, outside these workflows. Then configure the package's GitHub Trusted Publisher: owner `openai`, repository `mcp-extensions`, filename `release.yml`, environment `npm`, with direct publishing allowed. Select **Require two-factor authentication and disallow tokens** in package publishing access, and remove unused publishing tokens. Team releases then use OIDC without per-developer npm membership. [npm Trusted Publishers](https://docs.npmjs.com/trusted-publishers/).
5. Enable `RELEASE_PLEASE_ENABLED=true` after the selected GitHub authentication mode is ready. Infrastructure-only `ci:` changes intentionally do not create release PRs. For the first publication, merge a reviewed preparation PR touching the relevant package path (for example its README), with the final squash message `chore: prepare initial Python release` or `chore: prepare initial Node release` and a separate `Release-As: 0.1.0` footer. This requests the initial component tag even though the manifest already says `0.1.0`; use this only before that package version has been published. The rehearsal covers both initial-release cases. Keep both publishing switches off while reviewing the first release PRs, resulting tags, CI artifacts, and public-launch readiness. Enable each registry independently only after its setup and launch approval are complete.

All uploads from these workflows are **public**. PyPI's empty project name is already discoverable, but no distributions were uploaded during setup. npm publication with `--access public` also makes a previously private package public. A private GitHub repository does not make registry uploads private. npm generates provenance only when the repository is public and the tested source commit equals the workflow commit. npm derives its signed source reference from the workflow SHA, so rebuilding an older tag after main advances explicitly disables provenance to avoid attesting to the wrong source commit. OIDC authentication still applies. Provenance is also disabled for private repositories, which npm does not support. PyPI attestations remain enabled by default.

## Normal release and recovery

1. Land changes using Conventional Commit squash messages (`fix:`, `feat:`, `feat!:`). Release-please attributes changes by package path. Shared infrastructure changes may need an explicit package release decision; they do not inherently bump both libraries.
2. Review the relevant release PR. In default `GITHUB_TOKEN` mode, approve its workflows when prompted after creation or updates, and wait for CI before merging. Python and Node PRs can propose different versions and merge independently. The bot updates the package metadata, its changelog, and its manifest entry.
3. Review the checked commit and artifacts, then approve the corresponding publishing environment. A new release can still be built and reviewed while its registry switch is disabled.
4. For a build-only rehearsal or a retry, run **Actions → Release packages → Run workflow** on **main**, choose `python` or `node`, enter its existing component-tag version (without a prefix), and leave `publish` unchecked. This rebuilds the tagged commit, not the latest code on main. To upload later, run it with `publish` checked; repository identity, registry switch, CI, and environment approval still apply.
5. Verify the published version and fresh installation from the registry. Do not republish a successful version. There is no blanket skip-existing behavior: inspect a partial publication and recover only missing files from the original checked artifacts, or release a new version for a code fix. Python and npm failures can be retried independently.

The rehearsal uses release-please 17.6.0, matching the library bundled in the pinned action. Update both together. Bot-generated changelogs are excluded from Prettier so the first release PR can pass formatting checks.

No production upload is required to test this PR. The historical `v0.1.0` tag predates these workflows and is not a supported manual-release target. Never move or recreate a published package tag; fix release content through a new version.

## Why release-please

Release-please is optional for OIDC publishing, but this repository now adopts it for both packages. Like the OpenAI [Python](https://github.com/openai/openai-python/blob/main/.github/workflows/create-releases.yml) and [Node](https://github.com/openai/openai-node/blob/main/.github/workflows/create-releases.yml) SDKs, it maintains reviewable version/changelog PRs and creates releases after those PRs merge. Those SDKs use a GitHub App; this repository defaults to `GITHUB_TOKEN` and supports the App as an opt-in. It reduces bookkeeping, keeps release notes with version edits, and lets maintainers choose release timing. CI and registry publication remain explicit workflow responsibilities. Package validation and publication follow release-please outputs in the same workflow run, so they do not depend on token-created tags or releases triggering another workflow. Review the generated versions, especially before 1.0: features bump the minor version, fixes bump the patch, and breaking changes follow the configured pre-1.0 policy.

The team owns GitHub settings and release approvals; existing OpenAI registry administrators own publisher configuration.
